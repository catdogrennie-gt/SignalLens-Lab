# 基础行锁等待：真实发现、报告与恢复

本例验证一个直观的普通数据库问题：两个隔离测试会话竞争同一行，出现真实 InnoDB 记录锁等待。平台从 Zabbix 自主发现问题，生成 AI 报告；关闭后连续两次完整快照确认等待链为空。**基本锁等待及请求方、阻塞方关系已核对，具体 SQL 与完整根因未确认。**

## 数据如何进入平台

复用既有隔离实验室和 Zabbix 只读来源，单独建立“MySQL 行锁等待”对象，仅选择一个主机的三项数据：

| 监控项 | 用途 | 来源 |
| --- | --- | --- |
| `dbops.mysql.lock_snapshot` | 完整的当前等待链快照 | `performance_schema` 只读扩展，5 秒采样 |
| `dbops.mysql.lock_waits` | 当前等待数量 | 同一只读扩展，5 秒采样 |
| `mysql.threads_running` | 运行线程数 | 官方 MySQL 模板 |

扩展快照包含完整性和行数声明，平台验证 `db-evidence-lock-snapshot-v2` 契约后才用完整空快照判断恢复。平台每 10 秒读取所选数据、每 5 秒检查问题；没有手工提交采集任务或 AI 分析，也未给模型发送场景答案。本例没有核查 Zabbix 告警事件，因此不声称“Zabbix 未发现”。

## 怎么查看、操作

在分析平台首页选择“MySQL 行锁等待”，或从“最近已恢复的问题”进入“存在数据库锁等待”，再打开原报告及证据。访客账号只读；演示地址和账号见 [分析平台说明](https://github.com/catdogrennie-gt/db-evidence-platform)。

本次故障由既有固定行锁发生器的唯一开关控制，新多场景页面尚未集成该开关。故障触发入口当前只供内部验证，暂无公开开关。运维人员在内部环境打开既有开关后，等待平台自然采样和发现；关闭后观察新快照归零。发生器只操作隔离目标的一条固定测试记录，专用账号最多两个会话，退出执行回滚。本轮还配置了运行期限和独立截止清理，故障已关闭；不要将历史报告误认为当前仍有故障。

## 分析边界与后续改进

报告的现象、表层原因主要正确，但一个候选假设把请求侧的 `X,REC_NOT_GAP` 锁模式归给阻塞方。原始快照只能证明请求侧的模式；这一措辞缺口保留在验收记录中，不将“报告完成”标成完全诊断通过。单个冻结正快照也不能说明持续多久或后来是否恢复，恢复结论来自随后独立的新采样。

后续应补充经授权的会话到语句关联，进一步核对具体 SQL 和事务行为；不要仅靠锁等待数量猜根因。机器记录见 [basic-row-lock.json](basic-row-lock.json)，其中 `workflow_verified=true`、`basic_lock_relationship_verified=true`，`diagnosis_verified=false`。
