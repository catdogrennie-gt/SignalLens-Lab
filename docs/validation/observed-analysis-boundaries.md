# 真实工作流与分析边界

以下三项在2026-11-12串行运行，A只控制真实有界负载，B通过普通Zabbix取数和检查自主发现。每项分别记录直接清理和后续监控回落，未把人工预置的场景答案交给模型。工作流已验证，根因准确性未通过；原始报告保留，下面的人工复核不会改写原报告。

## SQL效率变化

**业务现象：** 请求p95约2.31→22.58→1.35ms；每次执行扫描行数20→4799→20。变化存在于短时业务请求和查询代价中，没有演示生产事故。

**本次Zabbix覆盖边界：** 实际窗口未产生新的触发器事件；官方慢查询速率9个样本均为0，现有慢查询规则为5分钟内的最小速率大于3。当前规则没有提示这次查询相对变慢，不代表Zabbix无法配置更细的查询效率规则。

**平台实际证据和限制：** 普通检查发现4个新变化信号，约90.5秒观察到关联本轮2个信号的新报告，OFF后直接清理与监控回落分别验证。模型给出扫描模式变化的候选解释，未确认具体SQL或根因；复核发现部分复合事实引用不全、因果用语偏强、峰值与末值混用。见[机器记录](query-efficiency-iteration3.json)。

## 应用连接池等待

**业务现象：** 应用池6/6被占用，取连接等待600ms、队列24、错误比例1，请求p95最高约7.79秒；数据库全局连接持续9/40。OFF后池、队列与错误回落。

**本次Zabbix覆盖边界：** ON至恢复窗口未产生新的触发器事件。实际MySQL拒绝连接规则关注数据库因连接上限拒绝连接，本轮阻塞在应用池；当前扩展应用指标没有配置相应触发器。可以用Zabbix补充应用池规则，不能将这说成监控工具本身做不到。

**平台实际证据和限制：** 普通检查发现8个新变化信号，约83.5秒观察到新报告，直接清理与监控回落均独立验证。模型提示连接获取瓶颈，但输入仅保留3个信号和1个数值摘要，遗漏已采集的池容量。报告把投影中省略的中间点写成上游缺采，又把连接数最大值11误作样本数（实际保留138点、原149点）。模型未收到最大连接数，不能把另一处实际9/40的人工观测当作模型已有的反证。见[机器记录](pool-pressure-iteration1.json)。

## 报表临时表代价

**业务现象：** 请求p95约1.48→44.19→1.20ms，DB调用p95约1.29→44.02→0.96ms；磁盘临时表0→约4.01→0个/秒。错误比例始终为0，本次是延迟和代价上升，不能描述为服务中断。

**本次Zabbix覆盖边界：** ON至恢复窗口未产生新的触发器事件。官方已有磁盘临时表规则：连续5分钟速率的最小值大于10。本轮约4个/秒、ON约120秒，没有达到这条实际配置；不是官方模板没有临时表告警。

**平台实际证据和限制：** 普通检查发现8个新变化信号，约119.8秒观察到新报告，直接清理与监控回落均验证。输入只保留3个较晚的延迟/查询速率信号与1条官方临时表摘要，遗漏25条数值摘要；模型还忽略了这条约4个/秒的临时表证据，只给出延迟/QPS相关和泛化查锁建议，甚至暴露内部字段名。临时表机制分析尚未通过，下一轮应改进证据预算分配、按指标保留上下文与用户建议，再复测。见[机器记录](temporary-work-iteration1.json)。
