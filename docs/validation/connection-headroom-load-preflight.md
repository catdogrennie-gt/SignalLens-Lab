# 连接占用场景：先保证负载能安全成立

## 实际发现的问题

2026-11-13 的 CAPACITY-05 中，新增监控连接使正常基线达到约 10/40。原负载固定申请 25 个连接，观察连接也计入容量；服务要求初始至少保留 6 个空位，因此正确拒绝申请。真实采样保持 10/40，没有形成连接水位风险。

这一轮是**复现未成立**，不能评价为平台漏诊，也不能把“开关已打开”当成故障已发生。负载已关闭，持有连接为零；取得后续低位配对样本，临时巡检周期已还原。

## 最小改进

私密服务配置支持可选 `hold_count`，只接受 1–25 的整数，默认仍为 25。部署者可以根据实际基线减少固定占用量；HTTP 开关不接受数量、目标或 SQL。初始 6 空位、运行至少 4 空位、固定 MySQL UUID 与 40 连接容量校验、owner/代次及短租约保护保持不变。禁止通过降低保护余量或终止监控连接来强行复现。

本次隔离服务设为 23，仅滚动独立负载容器；数据库、A 控制器及公开 B 不重启。OFF 状态、配置与代码校验已核对，尚不能由此宣称诊断通过。

## 操作检查

1. 确认开关关闭、无持有连接、没有另一位实验 owner。
2. 读取三组新鲜的连接使用量/上限配对，核对正常基线。预检须为观察连接额外留出一个槽位，并满足 `基线 + 固定占用 + 1 <= 上限 - 6`；不足即跳过。
3. 预先规定要跨越的关注水位，核对已选监控项、读取权限、自然巡检、队列与额度。保护余量足够但不能产生预期现象时也应跳过。
4. 设置独立有界清理护栏，只开启一次；用故障后实际样本确认效应，再考察平台发现与分析。不开手动 AI 报告来替代自然发现。
5. 关闭后分别确认零持有连接、后续采样恢复和原周期还原。报告标题、风险解释与引用另行验收。
